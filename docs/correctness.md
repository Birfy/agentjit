## 1. 根本困难：循环论证

生成的代码对不对，只能靠测试用例。但用例从哪来？

如果用例也由同一个模型生成，就出现循环：**模型误解了需求 → 它写的代码和它写的用例基于同一个误解 → 全部通过 → 交付一个自洽的错误。** 而且这种错误最难发现，因为它不会崩、不会报错，只是安静地算错。

**你没法从一个模型自己的理解里 bootstrap 出正确性。** 任何"让 LLM 写测试来验证 LLM 写的代码"的方案，只要两者共享同一份需求理解，就没有增加任何信息量。

所以核心问题是：**哪里能拿到不依赖模型理解的判据？**

有五个来源，可靠性和成本各不相同。它们不是备选项，是**叠加**的关卡。

---

## 2. Oracle 分层

| 层 | Oracle | 需要标准答案? | 成本 | 能抓什么 | 何时用 |
| --- | --- | --- | --- | --- | --- |
| **T1** 调用方例子 | 人/agent 给的 I/O 对 | 是 | 0（调用方出） | 语义错误，最强 | 有就用 |
| **T2** 变形性质 | 从需求推出的不变量 | **否** | 低 | 语义错误的一大类 | 总是 |
| **T3** 差分测试 | N 个独立实现互相比对 | **否** | 中 | **歧义定位** | 预估调用量大时 |
| **T4** 影子执行 | LLM 慢路径当参照 | **否** | 高 | 真实分布上的语义错误 | 高价值函数 |
| **T5** 属性/模糊 | schema 随机输入 | 否 | 极低 | 崩溃、schema 违规、边界 | 总是 |

关键判断：**T2 和 T3 被严重低估了，它们不需要标准答案却能抓语义错误。** 整个设计不应该押在 T1 上。

---

## 3. T1 — 调用方例子

最强，但最稀缺。规则见 [design.md §6.2](design.md#62-例子即规格--本设计的核心主张)：无例子不进持久缓存。

要点：**别指望调用方出很多题。** 两三个例子就是上限。所以 T1 的定位是"锚定语义"，不是"覆盖输入空间"——覆盖靠 T2 和 T5。

---

## 4. T2 — 变形性质：一条性质抵一万个用例

这是本文档最重要的一节。

**变形性质（metamorphic relation）是"不知道正确答案也能检查"的约束。** 你不知道 `f(x)` 应该等于多少，但你知道 `f(shuffle(x))` 必须等于 `f(x)`。这句话可以拿去检验**任意生成的输入**。

用户给 3 个例子，只验证了输入空间里的 3 个点。用户确认 3 条性质，验证的是整个输入空间。**这是几个数量级的差距，而对调用方的认知负担反而更低——判断"打乱行序结果应该不变吧？"比构造一组输入输出容易得多。**

### 4.1 这个领域的常见性质

本系统的目标场景（解析、清洗、转换、聚合、格式化、校验）恰好是变形性质最密集的领域：

| 性质 | 形式 | 适用 |
| --- | --- | --- |
| **置换不变** | `f(shuffle(xs)) == f(xs)` | 聚合、求和、分组、统计 |
| **守恒** | `sum(f(xs).values()) == sum(amounts(xs))` | 分组求和、拆分、路由 |
| **同态/可加** | `f(A ++ B) == merge(f(A), f(B))` | 分组聚合、计数、并集 |
| **幂等** | `f(f(x)) == f(x)` | 清洗、归一化、格式化、去重 |
| **单调** | `len(xs) 增加 ⇒ 对应 key 的值不减` | 计数、累加 |
| **空元** | `f([]) == 空结果` | 几乎全部 |
| **值域封闭** | `keys(f(xs)) ⊆ types(xs)` | 分组、映射、分类 |
| **往返** | `decode(encode(x)) == x` | 序列化、编解码、转换 |
| **大小关系** | `len(filter(xs)) <= len(xs)` | 过滤、去重 |

### 4.2 性质从哪来

三条路，按可靠性排序：

1. **调用方直接声明** — 最可靠，但要主动想，很少有人会
2. **模型提议 + 调用方确认** — **主路径**。模型从需求提出候选性质，调用方逐条确认/否决。确认一条性质是个二选一判断，比写测试用例便宜一个量级
3. **模板匹配自动推定** — 从需求意图匹配上表（"分组求和"→ 自动带上置换不变 + 守恒 + 空元）。**只在被调用方确认后才计入验证等级**，未确认的降级为"警告性检查"：失败时记录并提示，但不阻断

**不要把未确认的性质当作硬门槛。** 模型提出的性质本身也可能是错的（它可能提出"排序稳定"而实际需求不关心顺序），拿一个错的性质去否决一份正确的代码，会让系统在正确的地方卡死——而这类失败比漏过一个 bug 更难排查。

### 4.3 性质怎么检验

对每条确认的性质，用 schema 随机生成 N 组输入（默认 200），逐条检查。生成器要偏向边界：空集合、单元素、重复键、零值、负值、超长字符串、特殊字符、极端数值。

失败时报告**最小化反例**（delta debugging 收缩到最小失败输入）。"在 `[{type:"a",amount:"-0"}]` 上守恒失败"比"在一个 200 行的随机输入上失败"有用得多，无论对模型修复还是对人排查。

## 5. T3 — 差分测试：它其实是歧义定位器

独立合成 N 份实现（不同 prompt 措辞、不同温度、可以不同模型），在生成的输入上跑，比对结果。

朴素理解是"多数表决"。**但它真正的价值不在投票，在于分歧点精确指出了需求里没说清楚的地方。**

```
输入:  {rows: [{type: "sale", amount: "-50"}]}
实现A: {sale: -50.0}      保留负数
实现B: {sale: 0.0}        把负数当异常滤掉
实现C: 抛异常

→ 需求里压根没提负数金额。三个实现各自猜了一种。
```

这直接给出了本系统开放问题的答案：

> **不要让调用方出题，让调用方裁决。**

```
问: "金额为负数时应该怎么处理？"
    [ 保留负值 ] [ 归零 ] [ 报错 ] [ 无所谓，这种数据不会出现 ]
答: 归零
→ 自动生成一个测试用例，永久进该函数的回归集
```

对调用方来说，这是个单选题，几秒钟的事；产出的却是一个**正中要害**的测试用例——它覆盖的恰好是真有歧义的地方，而不是调用方凭空想象出来的地方。质量比自己出题高得多。

**这应该是 T1 例子不足时的首选补充手段，而不是退而求其次的方案。**

成本是 N 倍合成 token（N=3 时约 3 倍）。对一个要调用 200 次的函数完全值回票价；对只调几次的不值得。所以按预估调用量决定是否开启，`compile_function` 可以接受一个 `expected_calls` 提示。

一致的部分也不是白跑：N 个独立实现在大量随机输入上全部一致，是个不弱的正确性信号（虽然不排除共同误解）。

## 6. T4 — 影子执行

高价值函数上线初期，两条路都跑：编译路径的结果返回给调用方，同时把同样的输入交给 LLM 慢路径，比对。

这是唯一在**真实输入分布**上验证的手段——T2/T3/T5 用的都是生成的输入，而真实数据的形状常常出乎意料。

```
一致率 >= 98% 且样本 >= 20  → 提升为 CONFIRMED
一致率 < 98%                → 不一致样本作为反例喂回重新合成
```

贵（每次双份成本），所以只对高调用量、高影响的函数开，且限 `IDEMPOTENT_WRITE` 及以下等级。

比对不能用字符串全等：结构化字段严格比，自由文本比语义相似度，数值给容差。

---

## 7. T5 — 属性与模糊测试

从 param schema 随机生成输入，只检查**不需要语义知识的东西**：

- 不崩溃、不超时、不超内存
- 返回值符合 return schema
- 不调用未授权的 facade
- 确定性：同样输入跑两次结果一致（抓住偷偷用了随机数或当前时间的代码）

极便宜，无脑开。抓不到语义错误，但能抓住一大批健壮性问题——而生成的代码最常见的毛病恰恰是"happy path 写对了，遇到空值/异常格式就炸"。

## 8. 测试集够不够强？

前面解决了"用例从哪来"。还有一个同等重要的问题：**跑过了能说明什么？**

3 个用例全过，可能意味着代码正确，也可能意味着这 3 个用例太弱。需要量化。

### 8.1 分支覆盖：未覆盖的分支就是未验证的代码

跑测试时开覆盖率统计。**生成代码的每一个分支都必须被覆盖，否则不给 `VERIFIED`。**

有未覆盖分支时，处理顺序很重要：

1. **优先让模型删掉它。** 生成的代码里充满了无用的防御性分支（`if not rows: return {}` 而后面的循环本来就处理得了空输入）。删掉比补用例好——**代码越小，需要验证的面越小。**
2. 删不掉（是真实逻辑），则针对该分支生成用例，走裁决流程确认期望输出。

这条关卡便宜、客观、无需语义知识，而且顺带把生成代码里的冗余分支压掉了。

### 8.2 变异测试：纯函数设计的意外红利

覆盖率只说明代码被执行过，不说明错误会被抓住。变异测试直接量化后者：**故意把代码改坏（翻转比较符、改算术运算、常量 ±1、布尔取反、删语句、改返回值），看测试集能不能抓住。**

抓不住的变异体 = 测试集的盲区。

```
mutation_score = 被杀死的变异体 / 有效变异体总数
VERIFIED 门槛: >= 80%
```

变异测试在正常工程里太慢没人用。**但在这里它是便宜的**，这是纯函数设计的意外红利：

```
一个 20 行的纯函数 → 约 50 个变异体
每个变异体跑 5 个用例 × 1ms = 5ms
总计 250ms
```

毫秒级。**完全负担得起，而且这是唯一不需要标准答案、还能量化"测试集强度"的手段。** 存活的变异体还能直接指导补用例——它明确告诉你"把第 7 行的 `>` 改成 `>=` 没人发现"，这就是缺失用例的精确描述。

## 9. 防过拟合：模型会对着测试集写代码

修复循环（[design.md §6.3](design.md#63-合成循环)）会把失败的用例反馈给模型。跑 3 轮之后，模型完全可能写出一份**只对这几个用例正确**的代码——极端情况是直接 `if input == X: return Y`。

三道措施：

**1. Hold-out 分割（硬性）**

测试用例分两份：

```
修复循环可见:  70%（至少 1 个）
Hold-out 验收: 30%（至少 1 个），修复循环完全看不到
```

Hold-out 只在最后验收时跑一次。**Hold-out 挂了不是"再修一轮"——那只会让过拟合更深。** 处理方式：允许一次 hold-out 轮换（换一组做保留集，重跑合成），再挂即判定合成失败。

用例总数少于 3 个时凑不出有意义的 hold-out，此时**必须**用 T2 性质或 T3 差分补足，否则不给 `VERIFIED`。

**2. 禁止硬编码答案（静态）**

静态检查：代码里不得出现测试用例输出的字面量。这挡不住聪明的过拟合，但能挡住最蠢也最常见的那种。

**3. 测试先行（顺序）**

初始用例集必须在代码存在之前确定，且生成用例的上下文里不含任何代码。这削弱（但消除不了）代码与用例的相关性。

修复循环里给模型看失败详情是必要的，不算违反——**关键是"用例集本身"不能被代码反向影响。**

## 10. 测试集是资产，代码是可再生的

这一条改变了 Registry 该存什么。

一个函数的核心资产**不是它的代码，是它的测试集**。代码可以随时用更好的模型重新生成；测试集是一点一点攒出来的，攒进去的是对需求的真实理解。

因此：

- **Registry 以测试集为中心。** 代码只是"当前通过该测试集的一个实现"。
- **模型升级 = 免费的全库重生成。** 拿新模型对所有函数重跑合成，用各自的测试集验收，通过就换掉。测试集越厚，这个操作越安全。
- **测试集单调增长。** 只增不减：

| 来源 | 时机 |
| --- | --- |
| 调用方例子 | 首次 compile |
| 确认的变形性质 | 首次 compile |
| 差分分歧的裁决结果 | 合成期 |
| 影子执行的不一致样本 | 上线初期 |
| **生产环境的 guard 失败输入** | **持续** |
| 人工排查发现的错误 | 持续 |

最后两条是长期价值所在：**每一次线上失败都变成一个永久的回归用例。** 函数越老，测试集越厚，重新生成越安全。这是个正反馈。

## 11. 验证等级门槛

| 等级 | 门槛 | 可缓存 | 可复用 |
| --- | --- | --- | --- |
| `EPHEMERAL` | 无 | ❌ | ❌ |
| `VERIFIED` | T1 ≥2 例（含 ≥1 边界）**或** T3 裁决 ≥2 条<br>+ T5 全过<br>+ 分支覆盖 100%<br>+ 变异得分 ≥80%<br>+ hold-out 通过 | ✅ | ✅ |
| `CONFIRMED` | `VERIFIED` + 确认的 T2 性质 ≥1 条<br>+（可选）T4 影子一致率 ≥98% | ✅ | ✅ 优先 |
| `QUARANTINED` | 曾 `VERIFIED`，运行时连续失败 3 次 | 保留 | ❌ |

注意 `VERIFIED` 那一行的 **"或"**：T1 例子和 T3 裁决是可互换的入口。这就是开放问题"如果调用方不给例子怎么办"的答案——**换一条路拿到同等质量的判据，而不是降低标准。**

## 12. 成本

以一个 20 行纯函数、5 个用例、3 条性质为例：

| 关卡 | 成本 |
| --- | --- |
| 静态检查 | < 10ms |
| T1 用例 | 5 × 1ms = 5ms |
| T5 模糊（200 输入） | 200ms |
| T2 性质（3 条 × 200 输入） | 600ms |
| 分支覆盖 | 一次带 profiling 的执行，~50ms |
| 变异测试（50 体 × 5 例） | 250ms |
| **执行类小计** | **约 1.1 秒** |
| T3 差分（可选，3 实现） | +2 倍合成 token |
| T4 影子（可选） | 每次调用双份成本 |

**除 T3/T4 外的全套验证在 2 秒内跑完，且不花 token。** 合成本身要十几秒和上万 token——验证在成本结构里几乎是免费的。

结论很清楚：**T1/T2/T5 + 覆盖 + 变异这一套无脑全开，没有理由省。** 只有 T3 和 T4 需要按价值判断。

## 13. 开放问题

1. **变异得分 80% 这个阈值是拍的。** 需要实测：门槛太高会卡住正确的代码（有些变异体是等价变异，语义上杀不死），太低则形同虚设。等价变异体的识别本身是个难题。
2. **变形性质的误报代价。** 模型提的性质可能是错的，拿它否决正确代码会在正确的地方卡死。目前靠"必须调用方确认才计入门槛"兜底，但确认本身有成本，调用方也可能点错。
3. **T3 的 N 取几，实现之间怎么保证真独立？** 同一个模型换措辞，相关性可能依然很高。不同模型能降低相关性但成本和工程复杂度都上升。
4. **裁决的中断成本。** 差分裁决要打断调用方。对 agent 来说这是一轮额外推理，对人来说是一次打扰。批量攒起来一次性问，还是发现一个问一个？
5. **schema 驱动的输入生成对复杂嵌套结构够不够用？** 简单结构没问题，深层嵌套 + 字段间约束（"`type` 是 refund 时 `amount` 必须为负"）靠 schema 生成不出有效输入，可能需要调用方提供生成器或约束描述。
6. **真实分布 vs 生成分布的差距。** T2/T3/T5 全在生成输入上跑。如果真实数据的形状和生成器差很远，这些关卡会一起失效——而 T4 是唯一的对冲，恰好又是最贵的。
